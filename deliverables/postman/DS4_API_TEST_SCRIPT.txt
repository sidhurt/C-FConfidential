THREE THINGS THAT WILL BITE YOU IN POWERSHELL
  1. -k is required. The certificate is an internal CA.
  2. URLs containing $ (like $metadata, $top, $format) MUST be in SINGLE quotes.
     In double quotes PowerShell eats $metadata as a variable and sends a broken URL.
  3. JSON bodies need \" escaping. Plain double quotes get stripped by PowerShell
     and SAP replies "Error while parsing an XML stream".

  Port 8000 does not work from outside. Use 44300 only.

 1. REACHABILITY  (no login - expect 401)
================================================================================

curl.exe -i -k 'https://vhresds4ci.sap.shreecement.com:44300/sap/opu/odata/sap/API_PURCHASEORDER_PROCESS_SRV/$metadata?sap-client=200'

  Expect: HTTP/1.1 401 Unauthorized
  401 is CORRECT here - it proves the server is reachable and demanding a login.
  Note: a wrong service name also returns 401, so never use 401 to prove a
  service exists.

 3. GET - read purchase orders
================================================================================

curl.exe -i -k -u "QNOVATE8:$SAP_PASS" 'https://vhresds4ci.sap.shreecement.com:44300/sap/opu/odata/sap/API_PURCHASEORDER_PROCESS_SRV/A_PurchaseOrder?sap-client=200&$top=5&$format=json'

  Expect: HTTP/1.1 200 OK
          {"d":{"results":[]}}

  Empty is CORRECT - DS4 has no purchase orders. The empty 200 proves routing
  and authorisation work. It does not prove the operation works.
  Note the OData V2 shape: the array lives at  d.results

 4. GET - deliveries and stock
================================================================================

curl.exe -i -k -u "QNOVATE8:$SAP_PASS" 'https://vhresds4ci.sap.shreecement.com:44300/sap/opu/odata/sap/API_OUTBOUND_DELIVERY_SRV;v=2/A_OutbDeliveryHeader?sap-client=200&$top=5&$format=json'

curl.exe -i -k -u "QNOVATE8:$SAP_PASS" 'https://vhresds4ci.sap.shreecement.com:44300/sap/opu/odata/sap/API_MATERIAL_STOCK_SRV/A_MatlStkInAcctMod?sap-client=200&$format=json'

  Both expect: HTTP/1.1 200 OK with an empty result set.
  The ;v=2 on the delivery service is REQUIRED. Version 2 is the ONLY version
  registered. Without it: HTTP 403, /IWFND/MED/170 'No service found ... version
  0001'. With it: 200 OK, 149,516 bytes, 12 entity sets. Verified 2026-08-19.

================================================================================
 5. FETCH CSRF TOKEN  (required before any write)
================================================================================

curl.exe -i -k -X GET "https://vhresds4ci.sap.shreecement.com:44300/sap/opu/odata/sap/API_PURCHASEORDER_PROCESS_SRV/?sap-client=200" -H "X-CSRF-Token: Fetch" -u "QNOVATE8:$SAP_PASS" -c cookies.txt

  Read the  x-csrf-token:  header from the output and paste that value into the
  commands below, replacing <TOKEN>.

  The token AND the cookie file must both be sent on the write. A token without
  its cookie is rejected, and the failure looks like an auth error rather than a
  CSRF error.


================================================================================
 6. POST - stock transfer order  (expect 400)
================================================================================

curl.exe -i -k -X POST "https://vhresds4ci.sap.shreecement.com:44300/sap/opu/odata/sap/API_PURCHASEORDER_PROCESS_SRV/A_PurchaseOrder?sap-client=200" -H "X-CSRF-Token: <TOKEN>" -H "Content-Type: application/json" -H "Accept: application/json" -u "QNOVATE8:$SAP_PASS" -b cookies.txt -d '{\"PurchaseOrderType\":\"UB\",\"CompanyCode\":\"1000\",\"PurchasingOrganization\":\"0001\",\"PurchasingGroup\":\"001\",\"SupplyingPlant\":\"PLQ3\",\"to_PurchaseOrderItem\":[{\"Material\":\"MAT18\",\"Plant\":\"PLQ1\",\"PurchaseOrderItemCategory\":\"7\",\"OrderQuantity\":\"1\",\"PurchaseOrderQuantityUnit\":\"EA\"}]}'

  Expect: HTTP/1.1 400 Bad Request

    APPL_MM_PUR_PO/064   Use purchase order type "Standard" ("NB") or a type
                         copied from "NB".
    APPL_MM_PUR_PO/065   Use a supported purchase order item category for item .

  This failure IS the finding, not a mistake. Their real STO type ZP06 is a copy
  of UB (T161-BREFN = UBF) and their live STO items carry EKPO-PSTYP = 7, so both
  errors apply to ZP06 exactly as they apply to UB.
  No purchase order is created.


================================================================================
 7. POST - same payload, document type changed to NB  (expect 065 only)
================================================================================

curl.exe -i -k -X POST "https://vhresds4ci.sap.shreecement.com:44300/sap/opu/odata/sap/API_PURCHASEORDER_PROCESS_SRV/A_PurchaseOrder?sap-client=200" -H "X-CSRF-Token: <TOKEN>" -H "Content-Type: application/json" -H "Accept: application/json" -u "QNOVATE8:$SAP_PASS" -b cookies.txt -d '{\"PurchaseOrderType\":\"NB\",\"CompanyCode\":\"1000\",\"PurchasingOrganization\":\"0001\",\"PurchasingGroup\":\"001\",\"SupplyingPlant\":\"PLQ3\",\"to_PurchaseOrderItem\":[{\"Material\":\"MAT18\",\"Plant\":\"PLQ1\",\"PurchaseOrderItemCategory\":\"7\",\"OrderQuantity\":\"1\",\"PurchaseOrderQuantityUnit\":\"EA\"}]}'

  Expect: HTTP/1.1 400 - 064 is GONE, 065 REMAINS.

  Only the document type changed. This proves 064 is purely about the document
  type, and that 065 is a separate, independent lock on the item category.


================================================================================
 8. POST - standard NB order  (expect neither 064 nor 065)
================================================================================

curl.exe -i -k -X POST "https://vhresds4ci.sap.shreecement.com:44300/sap/opu/odata/sap/API_PURCHASEORDER_PROCESS_SRV/A_PurchaseOrder?sap-client=200" -H "X-CSRF-Token: <TOKEN>" -H "Content-Type: application/json" -H "Accept: application/json" -u "QNOVATE8:$SAP_PASS" -b cookies.txt -d '{\"PurchaseOrderType\":\"NB\",\"CompanyCode\":\"1000\",\"PurchasingOrganization\":\"0001\",\"PurchasingGroup\":\"001\",\"to_PurchaseOrderItem\":[{\"Material\":\"MAT18\",\"Plant\":\"PLQ1\",\"PurchaseOrderItemCategory\":\"\",\"OrderQuantity\":\"1\",\"PurchaseOrderQuantityUnit\":\"EA\"}]}'

  Expect: HTTP/1.1 400
          APPL_MM_PUR_PO/088   Document currency is not determined

  Neither 064 nor 065. The service accepted the document type and the item
  category and moved on to real business validation.

  THIS IS THE MOST IMPORTANT SCREENSHOT.
  It proves the service is not broken and the empty test system is not the
  reason. A standard purchase order gets through. A stock transfer order does
  not. The restriction is deliberate API scope.
