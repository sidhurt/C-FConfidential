Recommendation

The pre-PGI span — shipment, shipment cost, cost release — should be one API call, not three. Not for elegance: because four of the six steps have no callable SAP interface at all, so custom development is required either way.

2.3What your status fields actually mean

A correction that matters

The field VFKK-STFRE has been understood as the “cost release” status. Read from the SAP dictionary, it is the account assignment status. And blank means “not relevant”, not “not done” — so a blank field never indicated a missed step.

FieldWhat it really means
STBERCalculation status
STFREAccount assignment status
STABRTransfer / settlement status

There is no release field on the cost document header. What the business calls “cost release” is technically the transfer of freight cost into Materials Management — which is why completing it produces a freight purchase order and a service entry sheet.

2.4How the documents link

Correction

It has been recorded that the cost document number equals the shipment number. It does not.

Cost documentActual shipment

21000050932100005099 — not 2100005093

The number ranges are similar enough to look interchangeable. Any reporting or reconciliation built on “cost document equals shipment” will silently produce wrong results.

The delivery service must be version 2

Version 1 exists under the identical name and lacks the batch-split operations. It would activate cleanly and then fail on first real use.

Billing cannot be created through the billing API

All eight of its data sets are marked not-creatable. Billing creation must go through a different service. Any design assuming otherwise needs correcting.

3.2The BAPIs

Fifteen interfaces were read from your system. All are callable remotely. Three are not released — SAP makes no commitment to keep their interface stable across upgrades. If any is adopted, that carries a named upgrade risk.

Your transport fields have a home

Vehicle number, driver name and mobile, LR/GR number and date, and the three weights are customer fields on the shipment creation structure. The specification currently parks them as belonging to an unidentified route. They belong to the shipment creation call.

Two practical notes. BAPI_SHIPMENT_CREATE has no test mode — its first execution creates a real shipment. And the freight estimate is not a delivery-only call: it requires a full in-memory shipment to be constructed, not just a delivery number and a transporter.

3.3What performs the middle steps

Steps 2 to 5 are performed by internal SAP function modules. We identified all of them by name:

StepSAP function module
Create cost documentSD_SCDS_CREATE
CalculateSD_SCD_ITEM_CALCULATE
Account assignSD_SCD_ITEM_ACCT_ASSIGNMENT
Settle / releaseSD_SCDS_RELEASE
PersistSD_SCDS_SAVE
The terminology, confirmed by SAP itself

SD_SCDS_RELEASE's own SAP description translates as “transfer of freight cost items” — not “release”. This is why completing it creates a purchase order and a service entry sheet in Materials Management.

SAP refuses to split two of these steps

SD_SCDS_CREATE calls SD_SCDS_SAVE internally. Creating and persisting the cost document is a single SAP operation. Exposing them as two endpoints would invent a boundary that does not exist.

The conclusion that drives our recommendation

Four of the six pre-PGI steps have no callable SAP interface.

Custom SAP development is therefore mandatory, regardless of how many endpoints we expose. This is a property of the system, not a design preference. “Use standard APIs instead” is not an available option for this span.

Method note: we state this as a finding from the searches performed — function-module name patterns and full-scope where-used analysis, each with a control to prove the search itself was working. We do not claim no such interface could exist anywhere.

0.18% is a small proportion, and we want to be straight about that. This is not a system in crisis. But it is the number that matters, for this reason:

This 0.18% is the best case. It comes from code running inside SAP, in the same program context, with no network between the steps, tuned over years of production use. It still leaves 10,496 documents stranded. An integration that splits these steps across a network boundary, with an orchestrator that cannot read the cost tables, will not do better.

At roughly 4,000 logistics calls per day, 0.18% is about 7 documents a day, 2,600 a year — each with freight cost calculated but never posted to Materials Management. No freight purchase order, no service entry sheet, no accrual cleared.

4.2Cost type is a required input, and it is not constant

Any call that creates a shipment cost document must supply a cost type. Four types behave differently in your system:

Cost typeObserved behaviour
Z001Completes fully — freight PO and service entry created
Z003Strands — this is the 10,496 population
Z006Calculates; settlement not relevant
Y003Calculated only
New information

On 17 August, cost release was described as “a tick inside the transaction, not a separate BAPI”. That is accurate in the user interface. But the callable form requires a cost type to be chosen and supplied — and the current specification has no field for it. This needs a decision: is it derived from the shipment, or does the caller send it?

4.3Settlement is not technically required before PGI

This was an open question. It is now answered, and the answer is not what was assumed.

Proven from your data

SAP does not block goods issue on unsettled freight cost. The example above proves it: settlement was relevant and incomplete, and the delivery was goods-issued and invoiced anyway.

What this means. “Release before goods issue” is a business rule, not a SAP constraint. If you want it enforced, the interface must enforce it — SAP will not. Equally, an orchestration that waits for settlement is imposing a constraint SAP does not impose. That should be a deliberate decision rather than an inherited assumption.

4.4This pattern is already implemented in your system

The internal function that creates cost documents is called from eight places, all of them custom code written for this landscape — and from no SAP standard program. One of them is a function module with this interface:

Input
Shipment numbermandatory
Cost typemandatory
Commit flagoptional

One shipment in, cost document posted, commit under the caller's control. This is the shape we are proposing, and it already exists and runs here — a useful feasibility proof.

Two things must be said about it

1. It belongs to a different programme — outside C&F scope — so we cite it as proof the pattern works, not as something CNF can simply reuse.

2. It returns nothing: no document number, no error. It cannot tell its caller what it created or why it failed. That is the one thing our version must do differently.

5.2The gap in the specification

The API-03 request section has field-level detail for every stage except the shipment and cost stage, which carries only a note that the route is unidentified.

That gap can now be closed. The request contract is the shipment-create structure including your vehicle, driver, LR and weight fields, plus the delivery reference, plus a decision on cost type. We will produce this as a correction report rather than editing the approved workbook.

6Our recommendation

6.1The question

For the span shipment creation → freight estimate → cost document and calculation → cost release, ending immediately before goods issue: does CNF call SAP once, or three times?

6.2Why one

1 · Custom development is required either way

Four of six steps have no callable interface. Three endpoints means three custom wrappers, not fewer. The only question is how many doors we cut, not whether we cut any.

2 · SAP has already merged two of the steps

Creating and persisting the cost document is a single SAP operation. Splitting it would invent a boundary that does not exist. This also matches what was agreed on 17 August — costing creation and release merged into one call.

3 · The state lives in SAP, so the caller cannot own it

Only SAP can answer “how far did this get”. Three calls means the orchestrator holding a state machine for data it cannot read. One call that reads those documents and continues from where it finds itself is safe to retry by design — the most valuable property this interface can have.

4 · The 10,496

Splitting the steps is survivable — SAP's own implementation survives it at 0.18%. But nothing about three endpoints makes that number smaller, and two things make it larger: a network between the steps, and an orchestrator that cannot see the cost tables.

6.3What the API returns

{ "shipment":        "1100605471",
  "costDocument":    "1100608871",
  "costType":        "Z001",
  "calculated":      true,
  "accountAssigned": true,
  "settled":         true,
  "freightPO":       "6000105831",
  "serviceEntry":    "1003382363",
  "stage":           "READY_FOR_PGI",
  "messages":        [ SAP's own messages ] }

Stage-level status, not a simple success or failure. Every step that completed is named with the document it produced. A failure returns the step it stopped at, plus SAP's own message — which is what the functional-versus-technical error split agreed on 17 August requires in order to route errors correctly.

6.4Three conditions we state alongside it

  1. It is not atomic, and cannot be. Once the shipment is committed it is committed; recovery is reversal, not rollback. This is equally true of one API or three — but it should be on the record now rather than discovered later. The word “rollback” used in the 17 August readout should be withdrawn.
  2. It is resumable, not fire-and-forget. Calling it again reads the existing documents, works out what already exists, and continues. This is what prevents duplicate shipments.
  3. The SAP side does not own process state. Process identity, stage history and replay protection belong to the orchestrator. SAP holds no cross-step process state and cannot undo a committed goods issue however the code is written.
