No SAP document was created, changed, posted, committed or reversed in either system. Every finding comes from reading metadata, function-module interfaces, repository indexes and existing document tables.

Why two systems

DS4 is where we are authorised to write, so it is where runtime certification must eventually happen — but it has almost no business data, which is itself a finding (see 7.2). The pattern throughout is therefore: learn the mechanism in DS4 (metadata, interfaces, repository indexes), observe the behaviour in QS4 (real documents, real statuses).

1.2What counts as evidence

This distinction is the difference between “we think” and “we know”, and it is what will be tested in the room.

Terms that get confused — and the difference changes the answer

Remote-enabled ≠ released. TFDIR-FMODE = R means callable over RFC. Release status is a separate attribute meaning SAP commits to interface stability across upgrades. Three modules here are remote-enabled but not released — adopting them is a supportability decision.

HTTP 200 ≠ business authorisation. A $metadata 200 proves registration, an active ICF node and a resolving alias. It proves nothing about whether the business operation will succeed.

Empty result ≠ no data exists. It means no rows matched that request under that user's authorisations.

2What SAP actually does before PGI

2.1The six states

The portal presents one action. SAP performs six independently committed state transitions. Each is a separate database commit; none can be undone by a rollback once committed.

#StateStored inProof it completed
1Shipment createdVTTK header, VTTP assignmentTKNUM exists
2Cost document createdVFKK header, VFKP itemFKNUM exists
3CalculatedVFKPSTBER = C + DTBER/UZBER
4Account assignedVFKPSTFRE = C + DTFRE/UZFRE
5Settled / transferredVFKP + MMSTABR = C, EBELN + LBLNI populated
6Goods issue (PGI)MKPF/MSEG, LIKPMaterial doc, movement 601; WBSTK = C

The shipment-level mirror

The shipment header carries its own summary of steps 3 and 5, which lets you assess a shipment without joining to the cost tables:

  • VTTK-FBGST — shipment cost calculation status
  • VTTK-ARGST — shipment cost settlement status

Shipment 1100605471: both C. Shipment 2100005093: FBGST = C, ARGST absent — calculated, never settled.

2.3Status fields — the correction that changes the project's vocabulary

Most important correction in this document

The project has treated VFKK-STFRE as the “cost release” field for weeks. It is not. It is the account assignment status.

Read from the data dictionary, not from field names. Domain texts via DD07T:

FieldDomainActual meaningblankABC
STBERSTBER_KCalculationnot relevantnot calculatedpartialfully calculated
STFRESTFRE_KAccount assignmentnot relevantnot completedpartialcompleted
STABRSTABR_KTransfer / settlementnot relevantnot transferredpartialfully transferred

Three consequences, each of which has already burned us

  1. STFRE is not release. The name resembles German Freigabe (release); the domain text says Kontierung (account assignment). Field names lie; domains do not.
  2. Blank means “not relevant”, not “not done”. An earlier analysis found 999 of 999 sampled documents blank on STFRE and concluded release never happens. Invalid — blank meant those documents were never supposed to be account-assigned.
  3. VFKK has no release field at all. It has exactly 18 fields. What the business calls “cost release” is the transfer step, STABR — whose function module is literally named for it (see 3.3).

2.4How the documents link — and a join that was wrong

Correction

Earlier project notes recorded FKNUM = REBEL = TKNUM — cost document number equals shipment number. This is false.

Cost doc FKNUMVFKP-REBELActual shipment
110060887111006054711100605471
210000509321000050992100005099 — not 2100005093
130010531013001053631300105363

The correct join is VFKP-REBEL → VTTK-TKNUM. The number ranges overlap closely enough that the two look interchangeable — exactly how the error got in. Any reporting or reconciliation logic keyed on FKNUM = TKNUM will silently produce wrong results.

Full linkage path: VFKK/VFKP → REBEL → VTTK → VTTP → VBELN → LIKP/LIPS → VBFA → material document and billing.

BAPI_SHIPMENT_CREATE — the input surface

Imports: HEADERDATA (BAPISHIPMENTHEADER), ITEMDATA, STAGEDATA, HEADERDEADLINE, STAGEDEADLINE, ADDRESS, HDUNHEADER, HDUNITEM, ITEMONSTAGE. Exports: TRANSPORT (shipment number), SHIPMENTGUID, RETURN.

The client's transport fields live here

BAPISHIPMENTHEADER carries the customer append fields ZZVEHICLE_NO, ZZDRIVER_NAME, ZZDRIVERMOB, ZZLR_GR_NO, ZZLR_GR_DATE, ZZGROSS_WT, ZZNET_WT, ZZTARE_WT. v1.8 §8 parked these as “belonging to the unidentified Stage-B route”. They are now placed — the shipment-create call is their request surface.

No simulation mode

There is no TESTRUN parameter. The first execution of this BAPI creates a real shipment. Plan the DS4 demo accordingly.

BAPI_SHIPMENT_COST_ESTIMATE — what it actually needs

Inputs: HEADERDATA, ITEMDATA, STAGEDATA, deadlines, plus DLVHEADER and DLVITEMS. Exports RETURNCOSTS and RETURN — and notably no TRANSPORT, consistent with creating nothing.

Not a delivery-only call

You cannot pass a delivery number and get a freight quote. You must construct an in-memory shipment. Any API-04 design assuming “send the DI and the transporter, get a price” is wrong about the input shape. Its non-posting behaviour is also asserted, not proven — we have not yet compared VFKK/VFKP key counts before and after a call.

How we know — and why the method matters

  1. RFC status: TFDIR-FMODE. Control: BAPI_SHIPMENT_CREATE returns R; every SD_SCDS_* module returns blank. The control proves we are reading the right column.
  2. Search completeness: patterns SD_SCD*, SD_SCDS*, *SHIPMENT_COST*, *SHIPMENTCOST*, BAPI_SHIPMENT*, V54*. An earlier narrow search using only *SHIPMENTCOST* found nothing and produced the incorrect claim “no such BAPI exists”.
  3. Where-used completeness: full scope, all object types selected. Control: where-used on SD_SCD_ITEM_CALCULATE returned SAP-standard includes LV54CF02 and LV54CF03 — proving the index covers standard code, so a custom-only result elsewhere is a real finding, not an index gap.
Phrase it as a claim about the search

The defensible sentence is: “no shipment-cost create or release BAPI was discovered through the searches performed” — patterns and where-used both listed. Never “no BAPI exists”.

The conclusion that drives section 6

Four of the six pre-PGI steps have no callable SAP interface. Custom ABAP development is therefore mandatory, regardless of how many endpoints we expose. This is not a design preference — it is a property of the system.

State the 0.18% yourself, first

If you present 10,496 as if it were systemic and someone divides by 5.77 million, the number turns against you and takes the rest of the briefing with it. Presented honestly it is a strong argument. Presented as a crisis it is a liability.

4.3Settlement is not a technical prerequisite for PGI

An open question for weeks. Now closed — and the answer is counter-intuitive.

Proven

SAP does not block goods issue on unsettled freight cost. Cost document 1300105310 has STABR = A — settlement relevant and incomplete — while its delivery 0080387199 shows WBSTK = C, PGI complete.

Why an earlier counter-example did not prove this

First attemptThe valid one
Delivery01809155350080387199
Delivery typeEL — not a dispatch typeZLF — real dispatch, same family as the settled reference
STABRblank = not relevantA = not transferred
ProvesPGI proceeds when settlement is irrelevant — trivially truePGI proceeds when settlement is relevant and incomplete

The distinction is the entire argument. Do not present the first version.

Design consequence: “release before PGI” is a business rule, not a SAP constraint. If CNF wants it enforced, CNF must enforce it. Equally, an orchestration that blocks waiting for settlement is imposing a constraint SAP does not impose — that should be a deliberate choice, not an inherited assumption.

Limit of the claim: it proves PGI is possible without settlement in this configuration. It does not prove no configuration anywhere in the landscape would block it.

6The decision: one pre-PGI API

6.1The question, stated precisely

Scope is shipment creation → freight estimate → cost document creation and calculation → cost release, ending immediately before PGI. Billing, e-invoice, e-way and the Hybris repair cron are outside this decision.

The question is whether CNF calls SAP once for that span, or three times.

6.2Why one — four arguments

1 · Custom development is required either way

Four of six steps have no callable interface. Three endpoints means three custom wrappers, not fewer. The choice is only how many doors we cut in the wall, not whether we cut any. “Use standard APIs instead” is not an available option — and we can now prove that rather than assert it.

2 · SAP has already merged two of the steps

SD_SCDS_CREATE calls SD_SCDS_SAVE internally. Splitting create from persist would invent a boundary SAP does not have. This also matches what the room agreed on 17 August: costing-document creation and costing release merged into one call, reducing four calls to three.

3 · State lives in SAP, so the caller cannot own it

Chain state is in VTTK, VFKK/VFKP and LIKP. Only SAP can answer “how far did this get”. Three calls means CPI or the portal holding a state machine for data it cannot read. One call that reads those documents and continues from where it finds itself is naturally idempotent — the single most valuable property this interface can have.

4 · The 10,496

Splitting steps is survivable; SAP's own implementation survives it at 0.18%. But nothing about three endpoints makes that number smaller, and two things make it larger: a network boundary between the steps, and an orchestrator that cannot see the cost tables.

6.3What the API must return

Modelled on the real completed chain in 2.2:

{ "shipment":        "1100605471",
  "costDocument":    "1100608871",
  "costType":        "Z001",
  "calculated":      true,           // VFKP-STBER = C
  "accountAssigned": true,           // VFKP-STFRE = C
  "settled":         true,           // VFKP-STABR = C
  "freightPO":       "6000105831",   // VFKP-EBELN
  "serviceEntry":    "1003382363",   // VFKP-LBLNI
  "stage":           "READY_FOR_PGI",
  "messages":        [ SAP message class + number + text ] }

Stage-level status, not a boolean. Every step that completed is named with the document it produced. A failure returns the step it stopped at plus SAP's own message — exactly what the two-class error taxonomy agreed on 17 August needs to route functional versus technical errors.

6.4Three conditions to state alongside it

  1. It is not atomic, and cannot be. Once the shipment commits, it is committed. Recovery is reversal, not rollback. Equally true of one API or three — so not an argument between them, but it will be held against the design later if nobody wrote it down now. The word “rollback” appeared in the 17 August readout; withdraw it before it is tested.
  2. It is resumable, not fire-and-forget. Re-invoking reads VTTK/VFKK/VFKP, determines what already exists, and continues. This is what prevents a duplicate shipment and what prevents another 10,496.
  3. The SAP wrapper does not own process state. No process id, no stage ledger, no replay store in ABAP. SAP holds no cross-step process state and cannot roll back a committed PGI however the ABAP is written. Process orchestration belongs to the orchestrator — which the 17 August meeting placed in Hybris.
On naming

The business stopped the ZCNF_* custom OData portfolio on 14 August, and v1.8 was rebuilt to drop those names. The engineering here is justified and the evidence supports it — but frame it as exposing internal SAP function modules that have no released interface, which is narrow and defensible. Presenting a new custom service tree reopens a decision that already went against the project.
